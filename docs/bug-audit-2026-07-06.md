## CRITICAL

### X1 — "Enable Audio" modal can permanently silence the listener  `CRITICAL`  🔧 fix-designed 2026-07-06
- **Where:** `frontend/src/services/infrastructure/AudioClient.ts` — `connectRemoteStream` (694-861), idempotence guard (701-711), `stopCurrentStream` (492-522, esp. `track.stop()` at 499); modal handler `frontend/src/ui/pages/ListenerRoom.tsx:371-391`.
- **Symptom:** listener taps "Enable Audio" and gets permanent silence, no error, no recovery except full reload.
- **Root cause (validated against current code):**
  - **iOS / non-anchor (autoplay blocked → element PAUSED):** the guard (701-711) requires `!paused`, so it falls through; the next step `stopCurrentStream()` runs `currentStream().getTracks().forEach(t => t.stop())` at line 499 — and the modal passed `audioClient.currentStream()` as `remoteStream`, so **it stops the very track it's about to play.** `track.stop()` on a remote consumer track is irreversible (`readyState='ended'`); the code then re-attaches the dead stream (748) and `elem.play()` (763) succeeds on a corpse → permanent silence.
  - **Android / anchor (muted pump already playing):** on retry the guard sees same-stream + `!paused` (muted pump plays) + `!ended` → **returns early at 710**, so `startAnchor()` / `audioCtx.resume()` never run inside the user gesture; the AudioContext stays `suspended` → silent, and the modal was already dismissed (`ListenerRoom.tsx:374` clears the flag before the call).
- **Validation:** ✅ CONFIRMED both paths by reading current code (`track.stop()` present at 499; guard requires `!paused` at 706; modal clears flag before retry at 374). Fits the "old iPhone couldn't connect" report: old iOS Safari almost always blocks autoplay → modal → tap → dead track → "didn't work."
- **Fix design (resolved 2026-07-06, grill):** the codebase already has the correct
  "unlock without destroying" primitive — `attemptResume()` (`AudioClient.ts:344-385`,
  used by OS-interruption/devicechange recovery) does `startAnchor()` → `audioCtx.resume()`
  → `elem.play()` and never stops tracks. The modal just calls the wrong function.
  1. **Add a public `resumePlayback(meta?)`** = the `attemptResume` sequence, purely
     **state-driven** (no UA/fingerprint branching — user: "should work for any device
     based on detected state"): `startAnchor()`; if `audioCtx.state !== 'running'` → `resume()`;
     if `elem.paused` → `play()`. **On success, mirror the `connectRemoteStream` success
     side-effects** (`setStreamState({playing:true})`, `setupMediaSession(...)`, and
     `startWebAudioRender` in anchor mode) so the cold-iOS case — where the first `play()`
     failed and media-session was never registered — gets lock-screen controls too.
  2. **Modal (`ListenerRoom.tsx:380`) calls `resumePlayback()`**, NOT `connectRemoteStream`.
     Clear `requiresUserGesture` only **after** it resolves successfully. Trust the tap —
     no re-verify/re-show loop (user: reload is the fallback if it fails).
  3. **Defensive:** in `connectRemoteStream`, gate `stopCurrentStream()`'s `track.stop()` on
     `incoming !== currentStream()` so the "new stream" path can never kill a live track
     even if called with a same-stream arg.
  - Regression matrix to verify (any device, state-driven): iOS Safari cold autoplay-block,
    Android Chrome anchor gesture-less, OS-interruption resume, Bluetooth/devicechange,
    reconnect-with-NEW-stream, DJ path.

### X2 — `try/catch` inside `Effect.gen` never catches → DJ publish-failure cleanup is dead code  `CRITICAL` ⭐  🔲
- **Where:** `frontend/src/services/application/UserService.ts:222-333` (`publishDJRoom`).
- **Symptom:** any DJ publish failure before producer creation → backend room stuck in Setup (no CloseRoom sent), leaked send transport (30s timer armed), `activeRole` stuck `'dj'`, "Connecting…" with no exit but reload.
- **Root cause:** a failing `yield*` in `Effect.gen` short-circuits the fiber; the JS `catch (error) { cleanupFailedDJConnection() }` at 326-333 never runs. **Empirically verified twice** against effect 3.19.12 (`catchRan:false, finallyRan:false`). Only `createProducer` (295-313) has a real `Effect.catchAll`.
- **Validation:** 🔲 code path traced by 2 agents + empirical effect test; re-confirm the exact lines still lack an outer `catchAll`.
- **Proposed fix:** replace `try/catch` with `Effect.catchAll`/`Effect.onError`/`Effect.ensuring` wrapping the whole flow (mirror `joinRoomAsListener:652-665`); delete the dead `catch`.

### X3 — Navigating away leaks the whole media pipeline + stale-connected no-ops future joins  `CRITICAL` ⭐⭐  🔲
- **Where:** `frontend/src/ui/pages/ListenerRoom.tsx:274-286`, `DJRoom.tsx:128-136`; `UserService.disconnect` (759-781); `MediaSoupClientLive` has **no finalizer** (`MediaSoupClient.ts:944`); stale-connected guard `UserService.ts:475`.
- **Symptom:** back-button / error-cancel / tab-close → **DJ microphone stays captured** (privacy light on); on Android the **anchor noise bed keeps running** + consumer/AudioContext leak; `webrtcConnectionState` stuck `STREAMING`; then joining a *different* room short-circuits the handshake → "connected" but hears the old room / silence.
- **Root cause:** `onCleanup` only calls `userService.disconnect()` which closes only the WS; nothing calls `mediaSoupClient.cleanup()` / `audioClient.stopStream()` / `resetRoom()`; `MediaSoupClientLive` is `Layer.effect` (no scoped finalizer), so runtime dispose doesn't help; the join guard (475) checks store flags, not `roomId` or a live consumer.
- **Validation:** 🔲 flagged by all 3 audits (very high confidence); re-confirm no `pagehide`/`beforeunload` handler exists.
- **Proposed fix:** role-aware full teardown in `onCleanup` (best-effort `leaveListenerRoom`/`closeDJRoom`); make `MediaSoupClientLive` `Layer.scoped` with a `cleanup()` finalizer; add `pagehide` fire-and-forget leave; make the join guard `roomId`-aware and verify a live transport/consumer.

### X4 — Wake-up recovery race + no recovery trigger while the page is visible  `CRITICAL` ⭐  🔲
- **Where:** `frontend/src/services/infrastructure/WebSocketClient.ts:717-725` (force-close on stale pong), `1028-1036` (`notifyVisibilityResume` doesn't stamp `lastPongAt`), `368-371` (reconnect success has no app hook); `UserService.ts:1050-1072` (`evaluate()` only on visibilitychange/pageshow/online).
- **Symptom:** the classic "unlock phone → still silent → lock/unlock again → audio returns"; and a screen-on WiFi/SFU blip silences listeners with no self-heal.
- **Root cause:** on unlock the backlogged heartbeat tick sees a stale `lastPongAt` and **force-closes a healthy socket** before the probe pong lands; a `wsAlive && transportDead → full re-join` then races that close; on failure nothing retries (no `evaluate()` after auto-reconnect, no transport `connectionstatechange` hook).
- **Validation:** 🔲 flagged by 2 agents; re-confirm the heartbeat/grace timing.
- **Proposed fix:** stamp `lastPongAt = now` (or grant a grace window) in `notifyVisibilityResume` before probing; add an `onReconnected` callback from `attemptReconnection` success → `evaluate()`; hook mediasoup `connectionstatechange` into `evaluate()`.

### X5 — sessionId is a deterministic device fingerprint → identical phones collide  `CRITICAL (party)`  🔧 fix-designed 2026-07-06
- **Where:** `frontend/src/services/domain/User.ts:190-218` (`fingerprintToSessionId`) + `generateHash` (171-185).
- **Symptom:** two guests on the same phone model+OS get the **same** `session-<hash>`; the backend treats guest B as guest A's reconnection and **tears down A's transport** (`room.rs:498-532`, `listener.rs:74-82`) → they knock each other offline in a loop.
- **Root cause (validated against current code):** the id is `btoa(djb2(screenW|screenH|colorDepth|UA|tzOffset|lang|langs|hwConcurrency|deviceMemory|platform|canvasFP|webglFP))`. **No `crypto.randomUUID`, no per-tab `sessionStorage`/`localStorage` random, no time component** — purely deterministic. Canvas/WebGL fingerprints identify device *model/GPU*, not individual units, so two identical phones hash identically.
- **Validation:** ✅ CONFIRMED — the code contains no anti-collision randomness (contradicts the assumption that "we designed the id so identical phones won't collide"). **NOTE:** does NOT explain a *lone* user failing to join (collision needs ≥2 identical phones); see the a)/b) analysis.
- **Fix design (resolved 2026-07-06, grill):** no web-accessible hardware signal is
  stable-per-unit yet distinct between identical models — so "stable + unique" must come
  from **generate-once + persist**, not from fingerprint entropy. Chosen: client-generated
  random id in **`localStorage`** (user confirmed: must survive reload; per-browser is fine).
  1. `getOrCreateDeviceId()`: read `localStorage['hushfm-device-id']`; if absent, generate a
     **UUIDv4 via `crypto.getRandomValues`** (NOT `crypto.randomUUID` — that's iOS 15.4+;
     `getRandomValues` is iOS 10+, matters for the old-iPhone widening goal), store, return
     `session-<uuid>`.
  2. **Fallback:** if `localStorage` throws/blocked (private mode) → fall back to the existing
     fingerprint id (keep that code) — accepts the rare collision only in that edge case.
  - Result: stable across reload/back-forth (frozen randomness, not per-session), unique per
    unit → collisions ~0. User priority: **collision is worse than churn**, and this design
    has ~0 collisions.
- **LINKED (separate fix, not this bug): server-side ghost-listener reaping.** User wants the
  server to NOT accumulate ghosts when a tab closes / the app crashes. The stable id fixes
  *reconnection identity* (reload → rebind, no new ghost), but a permanent leaver still needs
  server-side reaping. Currently `stale_listener_timeout=0` (never reaped); verify the
  listener WS-disconnect cleanup timer actually reaps on close, and consider a sane non-zero
  grace. Track as its own item (relates to X7 DJ-side + listener cleanup).

## HIGH

### X6 — Every backend-reported error = 30s frozen spinner; dead-room URL = infinite reconnect churn  `HIGH` ⭐  🔲
- **Where:** `WebSocketClient.ts:582-640` (pending requests keyed by success-event-type only; no `commandFailed`/`roomNotFound` subscriber — grep-confirmed none); backend room-missing branch `api/ws/mod.rs:512-522` closes with no frame.
- **Symptom:** any server-side error (room closing mid-join, codec mismatch, transport fail) → 30s "Connecting…" then a misleading generic timeout; the real error text is discarded. Dead room URL → battery-draining reconnect storm.
- **Proposed fix:** correlate `commandFailed`/`roomNotFound` to pending deferreds (or add request ids); backend sends `RoomNotFound`/`ListenerNotFound` before closing in the room-missing branch; client treats it as terminal.

### X7 — DJ WebSocket death never cleaned up on the backend → zombie public rooms  `HIGH`  🔲
- **Where:** `backend/src/api/ws/mod.rs:45-117` (`handle_room_socket` just `break`s; no DJ-disconnect timer, unlike the listener path).
- **Symptom:** DJ tab-close/crash → room stays public with a producer receiving no RTP; listeners hear silence forever and their recovery never fires (WS + transport both "healthy"); new guests still join the dead room.
- **Proposed fix:** on DJ socket close, start a grace timer that pauses/broadcasts `StreamPaused` and closes the room after timeout; optionally emit `djDisconnected` to listeners.

### X8 — Zombie / duplicate reconnect loops  `HIGH` ⭐  🔲
- **Where:** `WebSocketClient.ts:803-818` (every `onclose` spawns a loop, no single-flight), `1044-1108` (finalizer never sets `shouldReconnect=false`), `990-1015` (`forceReconnectNow` forks another).
- **Symptom:** a disposed runtime's reconnect loop keeps looping and re-registers a phantom listener on the backend; concurrent loops open duplicate sockets that fight over the backend `event_tx`.
- **Proposed fix:** finalizer sets `shouldReconnect=false` first; `forkScoped` the reconnect so disposal interrupts it; single-flight `reconnectInFlight` ref; establish-guard treats CONNECTING as busy.

### X9 — `listenerNotFound` only handled after a successful join  `HIGH`  🔲
- **Where:** subscription created inside `startListenerRecovery` (`UserService.ts:912-915`), started only after `joinRoomOperation` resolves (`ListenerRoom.tsx:244-271`).
- **Symptom:** fresh/direct-URL unknown session (recreated room) → backend flushes `listenerNotFound`+Close during the initial join, no subscriber yet → 30s hang + reconnect churn instead of fast-fail-to-lobby.
- **Proposed fix:** subscribe to `listenerNotFound` in `UserService.connect()` before the first join command.

### X10 — Lobby store drops room updates unless `listenerCount` changes  `HIGH`  🔲
- **Where:** `frontend/src/stores/lobby/lobby.store.ts:75-81` (`updateRoom` only writes when `listenerCount` differs).
- **Symptom:** `isStreaming`, `name`, `djName`, `tags` changes are silently discarded → RoomCard live/streaming dot + titles go stale until a count change flushes.
- **Proposed fix:** compare all relevant fields, or always replace (fine-grained reconciliation makes this cheap).

### X11 — Landing creation-error is un-dismissable  `HIGH`  🔲
- **Where:** `frontend/src/ui/pages/Landing.tsx:364-378` — ✕ calls `connectionAdapter.clearError()` but the error lives in the **lobby** store; the modal copy (474-480) has no dismiss at all.
- **Proposed fix:** dismiss via `lobbyAdapter.setCreationError(null)`; add a dismiss to the modal copy.

### X12 — Request correlation by event-type, not id  `HIGH` ⭐  🔲
- **Where:** `WebSocketClient.ts:605-640` — pending requests keyed by expected event type; `HashMap.set` overwrites.
- **Symptom:** two in-flight commands expecting the same event type orphan the first (30s timeout); an unsolicited server event of a pending type resolves the wrong request. Reachable once recovery re-join races an in-flight command.
- **Proposed fix:** correlation ids on the wire, or serialize commands per connection with a queue.

### X13 — Recovery coordinator start/cleanup race in ListenerRoom  `HIGH`  🔲
- **Where:** `frontend/src/ui/pages/ListenerRoom.tsx:244-271` — `startListenerRecovery` launched via `Effect.runPromise` in `createEffect`; `recoveryCleanup` assigned in `.then`.
- **Symptom:** unmount between start and resolution → 3 window listeners + 2 WS subs never removed; coordinator can `navigate('/')`/re-join a dead page. Possible double-start.
- **Proposed fix:** synchronous `started` flag; `onCleanup` handles the pending-promise case (`.then(c => c())`).
